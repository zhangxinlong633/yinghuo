# 业务、网络、运维分层，并用 bplib 编解码 BPv7

日期：2026-10-01

教学演示。节点之间的线上报文改成 BPv7 字节。业务、网络、运维各看各的字段。bplib 只负责把业务字段编成束、把束解回业务字段。保管、接触窗口、下一跳、确认仍由现有 Nest 守护进程完成。

## 目标

同一条报文在三个地方看起来不同：

- 业务看到目的节点、载荷、生存时间、是否已受理，以及收件箱里的源、目的、载荷、到达时间。
- 网络看到 EID、BPv7 CBOR、接触窗口和逐跳保管。
- 运维看到状态、时间线、存储深度，以及主块摘要和原始束长度。

Earth 发往 Mars 的路径、错开的接触窗口、逐跳确认、TTL 和重复 id 去重保持现有行为。变的是线上字节，不再是 JSON。

## 非目标

- 不把转发、LevelDB 保管、托管状态机交给 bplib。
- 不实现 LTP、TCPCL、接触图路由、BPSec、分片。
- 不在这一改动里改 endpoint / relay 角色，也不做「节点上的多项业务注册」。每节点一个服务号。
- 不修改 `k8s/`。
- 不静默退回 JSON。共享库加载失败时进程退出。

## 架构

三台进程仍是同一套守护进程。中间加一层编解码，不把转发交给 bplib。

1. 业务 API 和操作页只交换业务对象。
2. 应用适配按接触计划把节点名换成 EID，或把 EID 换回节点名。
3. 网络层在要转发时调用 bplib 编成 CBOR，在 ingest 时解 CBOR。
4. 运维摘要（状态、事件、主块摘要、原始束长度）与 CBOR 分开存放，打开时间线不必每次解整束。

bplib 以共享库接入。仓库里放一份薄的 C 包装，导出三个函数：

- `dtn_bp_encode(srcEid, dstEid, payload, createdAtMs, ttlMs) -> bytes`
- `dtn_bp_decode(bytes) -> srcEid, dstEid, payload, createdAtMs, ttlMs`
- `dtn_bp_inspect(bytes) -> version, srcEid, dstEid, lifetimeMs, byteLength`

包装内部使用 bplib 的建束与解析入口。若公开 API 必须先有一个节点实例，包装在进程内创建一个只用于编解码的实例，不使用它的存储、托管和转发。Node 用 `koffi` 加载该共享库（macOS 为 `.dylib`，Linux 为 `.so`）。构建脚本负责编译 bplib 及其已声明的依赖（QCBOR、OSAL），并把库放到守护进程能找到的固定相对路径。

## 地址

接触计划里每个节点增加 `eid`。缺省：

| 节点 | EID |
|------|-----|
| Earth | `ipn:1.1` |
| Relay | `ipn:2.1` |
| Mars | `ipn:3.1` |

服务号 `.1` 表示该节点上唯一的收件业务。计划改成 `dtn:` 形式时，映射跟着计划走，代码不写死方案名。未知 EID 拒收，并记一条运维事件。

## 数据流

发送：

1. `POST /api/send` 接受目的节点名、载荷、可选 TTL。响应只有 `{ ok, id, src, dst, payload, ttlMs }`。`id` 是业务相关 id，响应里没有 EID、CBOR、FORWARDING。
2. 应用适配把目的节点名换成计划中的 EID。
3. 网络层写入保管。接触关闭为 WAITING，打开为 FORWARDING。规则与现在相同。
4. 转发时编码为 BPv7，`POST /api/peer/ingest`，`Content-Type: application/cbor`。

接收：

1. 到达接触必须打开，否则 503，发送方回到 WAITING。
2. 用 bplib 解码。解码失败则 400，不落库，发送方回到 WAITING，并在当前窗口内按现有 1 秒间隔重试。
3. 目的 EID 属于本节点：解出载荷写入收件箱。业务 peek / recv 只返回源节点名、目的节点名、载荷、到达时间。
4. 目的 EID 不是本节点：保管后等下一跳窗口再转发，不进收件箱。
5. `/api/peer/ack` 仍是网络侧逐跳确认。业务 send 的「已受理」不等于「目的业务已收下」。目的到达只出现在运维时间线里。

`DTN_ALLOW_JSON_INGEST=1` 时，ingest 额外接受现有 JSON，便于旧双节点计划回归。默认关闭。即使打开该开关，编码出口仍是 BPv7，且 bplib 必须能加载。

## 失败

| 情况 | 行为 |
|------|------|
| 共享库无法加载 | 进程启动失败并退出 |
| 编码失败 | 业务 send 失败；报文不进入 FORWARDING |
| 对端解码失败 | 400，本跳回到 WAITING，窗口内重试 |
| 未知 EID | 拒收，运维事件记录该 EID |
| TTL 到期 | 保管节点标 EXPIRED；未投递的载荷不进入收件箱。这一改动不新增「没送到」业务回执 |

## 控制台

每个节点仍只提供 `/`。顶栏按层分开。

| 页 | 层 | 看见 | 不看见 |
|----|----|------|--------|
| 操作 | 业务 | 目的节点、载荷、TTL、已受理；收件箱的源、目的、载荷、到达时间 | EID、CBOR、转发状态、时间线、hex |
| 连接 | 网络 | 接触窗口、下一跳、本节点 EID、对端 EID、线上为 BPv7 | 载荷正文、收件箱 |
| 报文 | 运维 | 状态、当前节点、更新时间、时间线；主块摘要（版本、源 EID、目的 EID、lifetime）、原始束字节长度，以及前 32 字节的 hex | 不展示整束 hex |

概览只放运维计数和窗口状态。存储只显示深度和路径。操作页文案保持「发送」和「收件箱」。运维页称「束」。中英文都按这个叫法。

## 验收

接触窗口测试继续注入 `now`。编解码测试使用固定向量，不依赖三台进程。

- 计划含三个 EID；缺省为上表。修改计划中的 EID 后，编码出的目的 EID 跟着变。
- `POST /api/send` 的 JSON 响应只有 `ok`、`id`、`src`、`dst`、`payload`、`ttlMs`。
- 窗口打开后，下一跳收到的 body 能被 bplib 解出同一载荷和目的 EID，且 `Content-Type` 为 `application/cbor`。
- 无法解码的字节返回 400，不写入 bundles。
- 目的节点收件箱记录只有源、目的、载荷、到达时间。
- `GET /api/bundles/:id` 仍返回状态和时间线，并增加源 EID、目的 EID、lifetime、原始束字节长度。
- 操作页 DOM 不含 EID 字符串和 hex 摘要；连接页含本节点与对端 EID；报文页含时间线和主块摘要。
- 现有三节点场景仍通过：错开窗口、第一跳确认后 Earth 状态为 ACKED、Mars 到达写在事件里、TTL、重复 id 只留一份。

## 范围

这一份规格只覆盖编解码接入和三层可见性，适合单独做一份实现计划。角色模型（每台都转发、中继站可不注入业务）和「目的业务已收下」回执留在后续规格，不塞进这次实现。
